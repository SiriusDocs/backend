**Дата среза:** 2026-09-23
**Код:** `backend` @ `33180de`, `protos` @ `ad8ec13` (тег `v1.3.6`)
**Целевая архитектура:** [C4-architecture.png](C4-architecture.png)

Документ фиксирует, какая часть целевой системы реализована, какая начата, а какая ещё не существует. Всё ниже проверено по коду, а не по README: каждый из четырёх модулей на момент среза успешно собирается (`go build ./...`).

## 1. Целевая архитектура и покрытие

На диаграмме C4 (уровень Containers) система состоит из семи сервисов и трёх хранилищ. Сопоставление с текущим кодом:

| Контейнер на диаграмме | Реализация в репозитории | Статус |
|---|---|---|
| **API Gateway** — авторизация, выдача прав, маршрутизация | `api_gateway` | 🟡 частично: маршрутизация есть, авторизации и выдачи прав нет |
| **Auth service** — аутентификация, авторизация, назначение прав | `auth_service` | 🟡 частично: аутентификация есть, назначения прав нет |
| **Importing service** — импорт, парсинг, преобразование файлов | `template_service` | 🟡 частично: импорт и парсинг RTF есть, преобразования нет |
| **Document designer** — конструктор документов (статические поля, плитки, доступы) | `template_service` (`CreateTemplateParams`) | 🟡 зачаток: создаются таблицы-шаблоны, конструктора как такового нет |
| **Docs service** — заполнение документов | — | 🔴 не начат |
| **Group service** — группы сотрудников над документами | — | 🔴 не начат |
| **Changes service** — история изменений документов | — | 🔴 не начат |
| **File DB** — хранение «сырых» файлов и шаблонов | `file_service` + S3 (Timeweb) | 🟢 готов как сервис хранения объектов |
| **User DB** | таблицы `users`, `refresh_sessions` в общей БД `sirius_db` | 🟢 готова |
| **Changes DB** | — | 🔴 не начата |

Отдельно: `file_service` на диаграмме не выделен в самостоятельный контейнер — он появился в коде как реализация «File DB» и сейчас выступает фасадом к внешнему S3. При обновлении диаграммы его стоит нарисовать явно.

Итого из семи целевых сервисов: один можно считать готовым (`file_service`), три существуют в частичном виде, три не начаты.

## 2. Что готово

### 2.1 `protos` — контракты

Отдельный Go-модуль `github.com/SiriusDocs/protos`, подключается сервисами по тегу.

- Три контракта: `auth.proto`, `templates/temp.proto`, `file/file.proto`.
- Генерация через `make gen`, сгенерированный код закоммичен (`gen/go/...`).
- Последний тег — `v1.3.6`.
- Пароль в `auth.proto` помечен `[debug_redact = true]`, интерцепторы сервисов затирают такие поля в логах.

### 2.2 `file_service` — готов

Полностью реализован (в `CLAUDE.md` он всё ещё описан как пустая заготовка — это устарело).

- gRPC-сервер на порту `50054`, регистрирует `FileService`.
- Работа с S3 через `aws-sdk-go-v2`, path-style, эндпоинт Timeweb (`internal/storage/s3/timeweb.go`).
- Реализованы: `GenerateUploadURL` (presigned PUT), `GenerateDownloadURL` (presigned GET), `GetFileMetadata` (HEAD с корректной обработкой `NotFound`/`NoSuchKey` как «файла нет», а не как ошибки), `DeleteFile`.
- Структурное логирование с длительностью операции и статусом; внутренние ошибки не утекают клиенту (наружу — общий `codes.Internal`).
- Конфиг: `configs/server/local.yaml` + `.env` (есть `.env.example` — единственный сервис, где он заведён).

### 2.3 `auth_service` — база аутентификации готова

- gRPC на `44044`, PostgreSQL, миграции goose (таблица версий `auth`).
- Реализованы RPC: `Register`, `Login`, `GetNewTokens`, `GetProfile`, `GetAvatar`, `GenerateAvatarUploadUrl`.
- JWT HS256 с claims `user_id` и `role`; refresh-сессии хранятся в `refresh_sessions` (одна активная на пользователя, каскадное удаление).
- Пароли — SHA-1 с общей солью `SALT`.
- Аватары: `auth_service` — gRPC-клиент `file_service`. Ключ формируется как `avatars/user_<id>_<uuid>`, записывается в `users.avatar_key`, наружу отдаётся presigned-ссылка. Если S3 недоступен, профиль всё равно отдаётся, но без аватара.
- Схема БД: `users` (`id`, `username`, `email`, `hashed_password`, `user_role`, `avatar_key`, `creation_timestamp`), `refresh_sessions`.

### 2.4 `template_service` — импорт и парсинг работают

- gRPC на `44045`, PostgreSQL, миграции goose (таблица версий `temp`).
- `UploadAndParse` — приём файла client-stream'ом чанками, сборка в память с защитой от переполнения (лимит 20 МБ на уровне транспорта).
- Валидация формата по magic-байтам: `.rtf`, `.docx`, `.odt`; лимиты размера из конфига (10 МБ / 100 Б).
- Асинхронная обработка: задача пишется в `processing_tasks`, клиенту сразу возвращается `task_id`, парсинг идёт в горутине. Состояния `pending → processing → done|error`.
- `CheckStatus` — опрос статуса. Важная деталь: нераспарсенный файл возвращается как **успешный** gRPC-ответ со `status: "error"` внутри, а не как gRPC-ошибка.
- `CreateTemplateParams` — генерация `CREATE TABLE template_<uuid>` по пользовательской схеме полей, с защитой от SQL-инъекций через whitelist типов (`AllowedTypes`) и регулярки на имена таблиц и колонок (`ValidTableName`, `ValidColName`).
- Типизированные ошибки `domain.AppError` с единой точкой маппинга в gRPC-коды; наружу — безопасное сообщение, в лог — полный текст.

### 2.5 `api_gateway` — транспортный слой готов

- HTTP на `8080`, Gin, CORS из конфига, graceful shutdown.
- gRPC-соединения к `auth_service` и `template_service` устанавливаются на старте с `WithBlock()` — если бэкенд не поднят, gateway не стартует.
- Единый формат ответа `{status, message?, data?}`; обратный маппинг gRPC-кодов в HTTP-статусы централизован в `internal/lib/response`.
- Swagger-аннотации в хэндлерах, UI на `/swagger/index.html`, сгенерированные `docs/` закоммичены.
- Реализованные маршруты:

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/auth/sign-up` | регистрация |
| POST | `/auth/sign-in` | вход, выдача пары токенов |
| POST | `/auth/refresh` | обновление токенов |
| GET | `/auth/profile/:user_id` | профиль + ссылка на аватар |
| GET | `/auth/avatar/:user_id` | presigned-ссылка на аватар |
| POST | `/auth/avatar/upload-url` | presigned-ссылка на загрузку аватара |
| POST | `/temp/files/upload` | загрузка документа, старт парсинга |
| GET | `/temp/files/status/:task_id` | статус задачи |
| POST | `/temp/params/create` | создание таблицы-шаблона |

### 2.6 Сквозной сценарий, который работает целиком

Загрузка аватара проходит через всю цепочку: `браузер → api_gateway → auth_service → file_service → S3`, и обратно — presigned-ссылка, по которой фронт кладёт файл в S3 напрямую, минуя бэкенд. Это единственный на данный момент сценарий, где задействованы три сервиса сразу.

## 3. Что не готово

### 3.1 Критично: авторизации нет ни на одной ручке

Это главный пробел на сегодня.

- В `api_gateway` **нет middleware аутентификации вообще** — ни валидации JWT, ни извлечения `user_id` из токена, ни проверки роли. Заголовок `Authorization` только разрешён в CORS, но нигде не читается.
- Следствие: все девять маршрутов, включая профиль и загрузку аватара, доступны анонимно.
- Конкретная дыра: `POST /auth/avatar/upload-url` принимает `user_id` **в теле запроса**. Любой неаутентифицированный клиент может выпустить presigned-ссылку на запись в аватар произвольного пользователя и перезаписать `avatar_key` в его записи. `user_id` обязан браться из токена, а не из тела.
- `auth_service` токены выпускает, но валидировать их на входе gateway некому.

### 3.2 Ролевая модель не реализована

- Колонка `users.user_role` есть, но значение по умолчанию — `'user'`, а не `'PENDING'`, то есть модерации новых пользователей нет.
- RPC `AssignRole` и `ListPendingUsers` объявлены в контракте `auth.proto`, но **не реализованы** в `auth_service` и не проброшены в gateway.
- Команды создания администратора (`cmd/create_admin`) не существует — первого админа завести нечем.
- В целевой архитектуре «выдача прав» — ответственность API Gateway, а «назначение прав» — Auth service; ни та, ни другая пока не покрыта.

### 3.3 Три сервиса не начаты

`Docs service`, `Group service`, `Changes service` отсутствуют полностью — нет ни каталогов, ни proto-контрактов, ни записей в `ClientsConfig` gateway (остались только закомментированные заглушки в `internal/app/app.go`). Вместе с ними отсутствует `Changes DB`.

`Document designer` как отдельный сервис тоже не выделен: его функцию частично несёт `CreateTemplateParams` в `template_service`.

### 3.4 Незакрытые места в существующих сервисах

**`file_service`:**
- `CopyFile` объявлен в контракте, но закомментирован в реализации.
- Поля конфига `max_upload_size`, `allowed_content_types`, `upload_url_ttl`, `download_url_ttl` **читаются, но нигде не используются**: ни валидации MIME-типа, ни ограничения размера нет, а TTL ссылки захардкожен константой `defaultExpiryMinutes = 15` в gRPC-слое (там же оставлен `TODO: закинуть в конфиг`). Белый список MIME в yaml сейчас декоративный.
- В `config.Config` остался рудиментарный `MigrationsPath` — своей БД у сервиса нет.

**`template_service`:**
- Парсер — регулярка по RTF (`DOCVARIABLE`), помечен в коде как полузаглушка. `.docx` и `.odt` проходят валидацию по magic-байтам, но не парсятся.
- Рядом лежит мёртвый код `processMock`.
- Преобразование файлов «в формат, предназначенный для платформы» (по описанию Importing service на диаграмме) не реализовано — есть только извлечение имён переменных.
- Парсинг запускается с `context.Background()` — отменить задачу или ограничить её по времени нельзя.

## 4. Приоритеты на следующий шаг

Порядок предложен от «чинит безопасность» к «расширяет систему»:

1. **Middleware аутентификации в `api_gateway`** — валидация JWT общим `SIGNING_KEY`, извлечение `user_id` и `role` в контекст Gin, закрытие всех маршрутов кроме `sign-up`/`sign-in`/`refresh`.
2. **Убрать `user_id` из тела `POST /auth/avatar/upload-url`** и брать его из токена; то же правило применять ко всем будущим ручкам «про себя».
3. **Ролевая модель:** реализовать `AssignRole` и `ListPendingUsers` в `auth_service`, миграцию на дефолт `'PENDING'`, гейт по роли в gateway, команду создания первого администратора.
4. **Довести `file_service`:** задействовать `allowed_content_types`, `max_upload_size` и TTL из конфига, реализовать `CopyFile`, убрать `MigrationsPath`.
5. **Поднять `template_service` на `protos v1.3.6`**, чтобы версии контрактов сошлись.
6. **Первые тесты** — начать с того, что ломается тише всего: валидация имён таблиц и колонок в `template_postgres.go`, маппинг ошибок в `response.ParseGRPCError`, парсер RTF на фикстурах из `testing/`.
7. **Новые сервисы** в порядке зависимостей: `Docs service` (заполнение документов поверх готовых шаблонов) → `Group service` → `Changes service` вместе с `Changes DB`.
8. **Инфраструктура:** Dockerfile на сервис и полный `docker-compose`, `.env.example` для остальных трёх сервисов, разделение баз данных.
